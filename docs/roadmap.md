# Roadmap

## Milestones

| # | Milestone | Scope | Status |
|---|---|---|---|

| **M1** | Foundation + warehouse interface | Registries, server config, creative tab, datagen, inventory snapshot and capacity math, warehouse interface block, GameTest setup | Done |
| **M2** | Aisle | Crane dock, rails, controller, input and output stations, aisle geometry, stock index, membership and persistence | Done |
| **M3** | Crane logic | Jobs, reservations, job planner, crane state machine and motion, controller dispatch, requests and rerouting | Done |
| **M4** | Rendering, sounds, recipes | Animated crane renderer with partial models, held items, block and item models, sounds, item descriptions, recipes, translations | Done |
| **M5** | Robustness, Ponder, polish | Edge cases (blocks broken mid-job, full or removed targets, save and reload, no power), Ponder scenes, visual polish | Done |
| **M6** | Warehouse terminal + showcase world | Terminal block with a searchable stock screen and requests, playable showcase world (`runShowcase`) | Done |
| **M7** | Request batching | Repeated requests for one item at one station merge into a single crane trip | Done |
| **M8** | Storage location filters | Create filter slot on the warehouse interface that partitions the warehouse by item | Done |
| **M9** | Recipe rebalance | Revised recipes for the terminal, rails, crane and output station, with no two recipes sharing an ingredient set | Done |
| **M10** | Terminal redesign | Separate display side (chosen at placement, turned with the wrench) and crane intake side (derived from the aisle) | Done |
| **M11** | Production patterns, stage 1 | Production station with 3 x 3 patterns: the warehouse delivers ingredients to the player's machines and stores the result | Done |
| **M12** | Mechanical Arm interaction points | Create Mechanical Arms put items into the warehouse input and take them out of the output, terminal and production station | Done |
| **M13** | Ponder scenes for terminal, production station and storage filters | Four new scenes: placing a terminal, requesting at a terminal, feeding machines from a warehouse, and dedicating storage locations with filters; terminal and production station appear in the Ponder index | Done |
| **M14** | Display Link sources for stock displays | Four sources a Create Display Link can read: aisle summary and stock list on the controller and the terminal, the stock of a filter slot's item on the output and the interface, and the crane's status on the dock | Done |
| **M15** | Stock rules | Warehouse stock keeper with a minimum, a maximum and a reserve per item; the warehouse restocks its own minimums through a production station and stops ordering when a machine loses a batch; the terminal asks before one of your own clicks crosses a reserve or a maximum; two Ponder scenes teach the three numbers and the restocking | Done |
| **M16** | Storage location priorities | A priority 0-9 on each storage location, set by holding the click on its filter slot and drawn on the block: among the equally suitable locations the crane fills the highest first. Storing only — retrieval always takes the nearest source, and nothing already stored is ever moved | Done |
| **M17** | Warehouse output as a configurable port | The warehouse output becomes the warehouse's general **port**: it either **requests** what its filter names, or it **accepts** what the warehouse cannot keep. A redstone behaviour says when it acts — on a pulse, while powered, or unless powered, so an accepting port works with no wiring at all and a lever switches it off, and a requesting one keeps a machine supplied without a clock, with one trip at a time. A rank orders an accepting port against the storage locations: negative is the overflow behind all of them, positive diverts items before they are stored. An accepting port turns andesite where the crane reaches in and shows its rank on the back; nothing is ever destroyed, and a full port lets the input back up | Done |
| **M18** | Collecting: the crane picks items up from a machine | A third direction on the warehouse port: instead of waiting for a belt or a funnel, the warehouse **fetches**. Point a port at the inventory a machine drops its result into, set the Collect row with a wrench, and the crane takes the items and stores them — so a machine needs no return path back to the aisle and the production loop closes by itself. The same filter says what is fetched, the same redstone rows say when, and a collecting port turns **copper** where the crane reaches in. It stops by itself at a stock rule's maximum, it never hands items back out through a port, and it refuses an inventory the aisle already counts, so no collect-and-overflow loop can churn. A player's request always comes first, several collecting ports take turns with the warehouse inputs, and nothing is ever pushed into your machine | Done |
| **M19** | Optional chunk loading for aisles with work | An aisle may hold **its own chunks** loaded while it has something to do — a crane job, an open request, a production order including an automatic restock, and optionally a collection that is already running — so a warehouse that restocks itself (M15), hands surplus out (M17) or fetches from a machine (M18) keeps working after you walk away. **It is a chunk loader, and it ships switched off.** Once an operator turns it on it is bounded three ways (aisles per dimension, chunks per aisle, the longest single hold), an aisle over a cap holds nothing at all and behaves exactly as before, and every aisle lets go as soon as it is idle. Held chunks grow no crops and spawn no mobs. The controller's goggles say whether this aisle is holding and why, and `/wareworks chunks` lists every ticket the mod holds and can release them | Done |
| **M20** | Recursive production | Order an item whose ingredients have to be made first, and the **whole chain** is planned the moment you click: one ordinary production order per step, each at the station holding its pattern, all created at once — or the click is **refused and names the item** that is really missing. Every intermediate travels through a real storage location, so the warehouse still crafts nothing and there is no machine-to-machine shortcut. **A step waiting for an earlier step is handed nothing at all**, so a chain that fails does not leave half-sets of ingredients in three machines; giving up on any step ends the chain and says what that costs. There is **no depth limit** — a chain is bounded by how many orders one click may create, by how many ingredient items it may spend over all of them, and by a cycle check that refuses a chain coming back to itself before anything is converted; a click too large is made **smaller** rather than refused. The terminal shows a chain as **one line** with the step that is working and a panel listing every step with the **address of the machine** it runs at. A redstone port may start a chain too, one at a time. And the **safety stop now covers every kind of order**: the first time any machine swallows a batch, the warehouse stops making that item everywhere, says so on the station's own block, screen and goggles, on the controller and on an aisle display, and only a deliberate click at that station — or at a stock keeper's row — makes it again | Done |
| **M21** | Rails around corners ([issue #1](https://github.com/Richie1710/create-wareworks/issues/1)) | A warehouse is no longer one straight aisle but **one connected set of rails**: rails that touch connect, two runs at right angles make the block they share a **corner**, and the crane rolls onto it, swings a quarter turn with a rumble and a metal clack, and drives on. Every straight run is an **aisle** with its own letter — the first from the controller's value box, each further one the next free letter — and the letters and position numbers are pinned to the rails, so extending or shortening an aisle never reshuffles your addresses. **Racks in a corner work**, which is the whole point of not making corners travel-only: the corner block carries one rack on each of its two aisles, told apart by the one rule there is — point the interface away from the aisle it belongs to. One controller, one terminal, one stock list and one crane for the whole warehouse. A **wrench closes a rail**, which is how you keep a rail out of a warehouse (it no longer turns the axis, which stopped meaning anything the moment a second rail touched it). A **home point** is a block you place beside the rails to say "wait here": on a warehouse with more than one aisle the crane drives back to it after a configurable idle delay, drops the trip for real work at any moment, even mid-turn, and holds no chunk for it; without a home point the dock stays its home, and on one straight aisle the crane stands where its last job left it, exactly as before. **Your addresses, stock and jobs survive untouched** — the one thing that can change in a world you already built is that rails which merely touch now connect, so a stray rail joins the warehouse; the **wrench** closes it, and `aisle.maxBranches = 1` keeps every warehouse the single straight aisle it was. Not yet: rails that **split**, which is [issue #2](https://github.com/Richie1710/create-wareworks/issues/2) and the milestone after this one | Done |
| **M22** | One warehouse, many aisles ([issue #2](https://github.com/Richie1710/create-wareworks/issues/2)) | The rails may **split and close on themselves**: a T-junction, a cross, a ring and a comb of side aisles off one main run are ordinary warehouses, and the two "this needs a later version" messages are gone. A straight run through a junction stays **one** aisle with one letter however many aisles cross it, the three- and four-way cases are decided by the same facing rule corners already used, and goods from every aisle reach the **one** block you put your output on. With junctions there is more than one way from A to B, so the warehouse **searches for the cheapest** one — blocks driven plus quarter turns, at the same `crane.turnPenaltyBlocks` the crane drives at, exact, reproducible and derived only when the rails change — and a crane round a ring really takes the way the planner costed. An aisle a server limit cut loose keeps its addresses and its stock and **says on its own blocks** that the crane cannot reach it, instead of looking like a chest nobody wants. `aisle.maxJunctions` bounds what that search costs, and `controller.snapshotCycleTicks` bounds how long a big warehouse takes to re-read every location once — measured: the largest warehouse the settings allow comes round in 34 minutes instead of 2.3 hours, while every warehouse of up to about 1200 locations — every warehouse at the default aisle limits — reads exactly one location per turn, which is what every earlier version did, and a server that raised the aisle limits past that can have the old cadence back with `controller.snapshotCycleTicks = 0`. One dispatch run of a 64-location warehouse with four inputs holding three item types each now puts 68 questions to the world where it used to put 772. A Ponder scene, "Rails That Split", teaches the whole of it in the game, and every screen that speaks for the whole warehouse rather than for one of its aisles now says so. Not yet: **several cranes on one warehouse** — one crane drives out and back along every side aisle in turn, so a comb has the throughput of one machine, and that is the milestone after this one | Done |
| **M23** | Order a whole list from a clipboard ([issue #19](https://github.com/Richie1710/create-wareworks/issues/19)) | Hand the warehouse a **shopping list** instead of asking for one item at a time. Put a **clipboard** into the terminal's new list slot, press the list button, and the warehouse works the list off: it fetches what it can, **ticks each entry off on the clipboard as it delivers it**, and waits whenever the terminal is full instead of refusing — so a whole schematic's worth of material arrives in portions while you carry the crates to the site. The clipboard is the order and its receipt in one: pick it up and the ticks say what arrived and what is still outstanding. A **Schematicannon** writes its material checklist straight onto a clipboard, and a hand-written one works just as well. If the list wants more than the warehouse has, or if something on it would have to be **produced** first, it **asks before it starts** — the same dialog a request past a reserve raises, with the numbers for the whole list. Nothing new happens underneath: a list order is a stream of **ordinary requests** with one owner, so batching, reserves, maxima, filters, priorities, production chains and the safety stop all keep working unchanged, no item teleports, and the crane fetches every item physically. An entry the warehouse can neither stock nor produce is stepped over, left unticked and reported rather than blocking the rest of the list; a list that cannot be served at all stops measuring until you click it again | Done |
| **M24** | Sort the terminal's stock list ([issue #17](https://github.com/Richie1710/create-wareworks/issues/17)) | The terminal's grid has three orders and one button that cycles them: **most available first**, **most used** and **by name**, each with its own icon, and hovering the button says what the order means and which order the next press would give. "Most used" is the new one and the reason for the milestone — on a warehouse holding hundreds of item types it opens the terminal on the twenty items *you* keep fetching instead of the twenty it has the most of. Each request counts **once**, whatever amount it asked for, so one ctrl-click on a thousand cobblestone cannot outrank a hundred deliberate requests; a refusal counts nothing, and only a **player's** request counts at all — a redstone request at a port counts for nobody, because a port is not a player. The order you pick and what the terminal has learned are remembered **per player on the server**, so they are the same at every terminal of the world, they survive closing the game, and on a server everybody has their own. The store is **bounded** (`maxTerminalUsageEntries`, 64 item types by default) and an old habit **fades** as a new one grows, so the list follows what you are building now rather than what you built in your first week; until you have requested anything, "most used" simply *is* "most available first". The search, the "only what is available" filter and the offers a production station makes at zero stock all behave exactly as before — an offer stays behind everything really in stock in every order, and so does a row a stock keeper holds open for an item the warehouse has run out of, so the top of "most used" is never a row that cannot be ordered. Handing the terminal a **clipboard list** counts every item type on it once, and a list fetched again and again really does climb. New counts take effect the next time *you* ask for a list — a press of the button, a keystroke in the search, the filter — so clicking one cell twice always asks for the same item instead of the row sliding away under the cursor. What is remembered is bounded in size as well as in number, so an item carrying a whole inventory with it (a filled shulker box, a written book) never joins the order and nobody's save file grows by kilobytes per favourite. Not done: a fourth **recently requested** order, which the issue raises as a possibility and which would want a small menu rather than a fourth click on one button | Done |
| **M25** | Name your aisles ([issue #15](https://github.com/Richie1710/create-wareworks/issues/15)) and show the crane's throughput ([issue #16](https://github.com/Richie1710/create-wareworks/issues/16)) | Give an aisle a **name** with an item you already named in an anvil: right-click a **warehouse controller** and the aisle in front of it is called that, right-click a **warehouse interface** and the aisle *it stands in* is — so naming aisle B is a matter of clicking something that stands in aisle B, with no syntax to remember and nothing to type. A plain **name tag** takes the name off again, the item is never used up, and the action bar answers every click. The name then stands wherever the letter stands: the controller reads "Warehouse A — Ores" and gives each named aisle its name where it used to give a rail count, every block of the warehouse reads "Address: B-03-07R (Ores)" on its own goggles, and a Warehouse Summary display board gets one more row. The address itself never changes — the name stands beside it, because the address is what the terminal and every report speak. A name survives saving, a chunk unload, a dock you break and build again, and the aisle letter being scrolled; only breaking the controller takes it away. Until you have named anything, the controller's goggles say how. Not built, deliberately: **naming a single rack** (there is no face left to click and nowhere to read it) and **searching the terminal by aisle name**, which is sequenced rather than dropped. The other half: the crane says what it **got done**. Look at a **stacker crane dock** through goggles and it reports the last minute of its own work — "Busy: 78% of the last minute", "Blocked: 4%" whenever something really held it up, where that time went ("Travel 54% · turning 6% (9 corners) · at the rack 18%") and what came of it ("Trips: 9 · items: 412"). The numbers are honest about themselves: a crane loaded a moment ago says "of the last 23 s" and never scales nine trips up to a minute, a minute spent unloaded counts as neither work nor waiting, nothing is remembered across a restart, and a parked machine's tooltip reads exactly as it did before. The **warehouse controller** carries the two lines you came for, and a **Display Link** on the dock offers a second source, "Crane Throughput", with four rows that never move — "Measuring" until the machine has really run a minute. Not built, deliberately: any history, graph or command, and any "capacity" number, because most of a quiet crane's missing trips had nothing to carry | Done |
| **M26** | Packages at the door ([issue #18](https://github.com/Richie1710/create-wareworks/issues/18), first half) | Hand goods over as **Create packages**, and take them in. Put a **Create Packager** against a **warehouse port** — back of the Packager to the block, which is how it faces itself when you place it — hang a plain **sign** on it for the address, and what the warehouse puts in that port leaves as an addressed box; put the same Packager against a **warehouse input** and arriving packages are opened into the warehouse and stored. **Both of those already worked, and nothing in the game said so.** This milestone is the part that was missing: a Ponder scene, **“Packages at a Warehouse Door”**, that builds both doors in front of you and teaches the one rule that decides the direction — which station the Packager's **back** touches, which is also why you cannot wire one the wrong way round; goggle lines that name what a door does (**“Hands over as a package”**, **“Addressed to: Base North”**, **“Takes packages apart”**, **“Packages opened: 12”**); and, in gold, the two failures nothing else in the game mentions — a **Stock Link** on the Packager, which makes it ignore every redstone signal for ever with no message anywhere, and a package the input cannot hold **whole**, which until now simply sat in the funnel (**“Last package refused: stacks in it 3, free slots 1”**). A box holds up to nine stacks and a door sends about one a second, a stray item in the port rides along, a box addressed somewhere else is opened anyway, and a box that reaches an input with no Packager behind it is stored as an ordinary item. Nothing is saved, no setting changed and no old world is touched. Not yet: **ordering to a door at the terminal**, which is the second half of the issue and the milestone after this one | Done |

Feature requests are welcome there. Please add a reaction to an existing issue instead of opening a duplicate.
